报文 Packet

一个 TCP 报文段分为 首部 和 数据 两部分，而 TCP 的全部功能都体现在它首部中各字段的作用
TCP 报文段首部的前 20 个字节是固定的，后面有 4n 字节是根据需要而增加的选项 (n 是整数)
TCP 首部的最小长度是 20 字节
TCP 报文段长度 = TCP 首部长度 + 数据字段长度
最大报文段长度 MSS - Maximum Segment Size：每个 TCP 报文段中的数据字段的最大长度

确认位 ACK
1bit 标志位 Control Bits
Acknowledgment
本报文段包含一个有效的确认号，用于确认已成功接收到对方的数据
只有当 ACK = 1 时，确认号字段才有效。当 ACK = 0 时，确认号无效
除了最初的 SYN 报文（建立连接的第一个包），所有后续 TCP 报文都必须将 ACK 置为 1
是实现 可靠传输 的核心机制之一

2. 使用大小写区分；ACK表示控制位；ack表示确认号，如下例

立即位 PSH
1bit 标志位 Control Bits
推送 Push 操作
TCP 默认会缓冲数据以提高效率，但某些应用（如交互式命令行）希望数据立即被处理
提示接收方不要缓存，应立即将本报文段中的数据交付给上层应用程序
实际效果：现代操作系统通常忽略 PSH 标志，或将其视为普通数据，但发送方可设置它来建议“尽快上送”
重置位 RST
1bit 标志位 Control Bits
重置连接 - 强制关闭连接或拒绝非法报文
常见错误场景：

收到不属于任何现有连接的报文（如端口未开放）

应用程序崩溃，TCP 发送 RST 终止连接

检测到严重错误（如序号严重错乱）

RST 报文不需要确认，收到即断开
收到 RST 通常意味着连接异常终止（非正常四次挥手）
同步位 SYN
1bit 标志位 Control Bits
同步序号，用于建立连接
在三次握手过程中，SYN 用来协商初始序号
SYN = 1 表示这是一个连接请求或连接接受报文
SYN = 1，ACK = 0 时，表明这是一个连接请求报文段 - 连接未建立
SYN = 1，ACK = 1 时，表明这是一个连接接受报文段 - 连接建立；ACK 必须为1
SYN 报文本身不携带应用数据，但占用一个序号（seq 值 +1）
终止位 FIN
1bit 标志位 Control Bits
用来释放一个连接
发送方已完成数据发送，请求关闭连接
用于四次挥手 - 连接释放
FIN = 1 表明此报文段的发送端的数据已发送完毕，并要求释放运输连接

表示“我不会再发数据了”，但还可以接收数据（半关闭状态）

对方收到 FIN 后需回复 ACK，并在自己也无数据发送时发送自己的 FIN
正常关闭连接必须通过 FIN，而 RST 是异常关闭

可靠传输 Reliable

IP 网络本身提供的是不可靠的传输
可靠需求 Requirement
传输信道不产生差错
不管发送方以多快的速度发送数据，接收方总是来得及处理收到的数据
解决方案 Solution
可靠的本质是 确认 和 超时重传
序号 + 确认号：实现数据有序传输和重传机制的重要支撑
停止等待协议 ARQ
Automatic Repeat Request
每发送完一个分组就停止发送，等待对方的确认。在收到确认后再发送下一个分组
情况1：无差错

A 发送完分组 M1 后就暂停发送，等待 B 的确认 (ACK)

B 收到 M1 向 A 发送 ACK

A 在收到了对 M1 的确认后，就再发送下一个分组 M2

情况2：超时重传

如果：B 没有收到M1或者收到的M1经过检测是错的，那么就丢掉，不发任何消息

所以：A 收不到 B 的回复/确认

A 为每一个已发送的分组设置一个超时计时器

A 只要在超时计时器到期之前收到了相应的确认，就撤销该超时计时器，继续发送下一个分组 M2 - 节流

A 在超时计时器规定时间内没有收到 B 的确认，就认为分组错误或丢失，就重发该分组

情况3：确认丢失

B 所发送的对 M1 的确认丢失了，那么 A 在设定的超时重传时间内将不会收到确认，因此 A 在超时计时器到期后重传 M1

假定 B 正确收到了 A 重传的分组 M1。这时 B 应采取两个行动：
1.丢弃这个重复的分组 M1，不向上层交付
2.向 A 发送确认

情况3：确认迟到

B 对分组 M1 的确认迟到了，因此 A 在超时计时器到期后重传 M1

B 会收到重复的 M1，丢弃重复的 M1，并重传确认分组

A 会收到重复的确认。对重复的确认的处理：丢弃

特点
暂存：在发送完一个分组后，发送方必须暂存已发送的分组的副本，以备重发
编号。对发送的每个分组和确认都进行编号
超时重传。发送方为发送的每个分组设置一个超时计时器。若超时计时器超时位收到确认，发送方会自动超时重传分组
超时计时器的重传时间应当比数据在分组传输的平均往返时间更长一些，防止不必要的重传
简单，但信道利用率太低
连续ARQ协议
流水线传输：在收到确认之前，发送方连续发出多个分组
由于信道上一直有数据不间断地传送，流水线传输可获得很高的信道利用率

滑动窗口 Window

TCP支持全双工通信
通信的双方各自维护一个发送窗口和接收窗口，共4个窗口
简单起见，我们只考虑一个方向的通信
发送窗口
发送方维持一个发送窗口，位于发送窗口内的分组都可被连续发送出去，而不需要等待对方逐个确认
发送窗口滑动：发送方每收到一个确认，就把发送窗口向前滑动一个分组的位置；已确认的数据应移出窗口
累积确认 Cumulative Acknowledgment：接收方对按序到达的最后一个分组发送确认，表示：到这个分组为止的所有分组都已正确收到了
窗口大小以字节为单位
窗口大小由接收方B决定：通过 TCP 报文中的 Window 字段告知发送方A自己还能接收多少数据
[] 窗口应用
假设发送窗口大小 = 4，当前可发送分组 [1, 2, 3, 4]
发送 1 - 4
收到 ACK=3，表示 1、2 已收到，等待接收 3
1、2移出窗口，后面的分组补进来并发出去，等待确认
其它没有收到确认的 3、4，保留，以备超时重传
窗口滑动到 [3, 4, 5, 6]
[] 已知发送窗口大小为500，某主机收到的确认号为201。如果已经发送了300B的数据，则还可以发送多少数据？
发送了300B，对方确认了200B
还有100B没有确认
确认过的数据报被移出缓存，窗口仅仅保留没有确认的数据报
窗口还有100B等待确认
窗口大小是500，所以还可以发送 500 - 100 = 400B
接收窗口
接收方维持一个接收窗口，告诉发送方自己还能接收多少数据，用于 流量控制
根据接收窗口的大小动态通知发送方
窗口左侧是已经已经按序到达且确认过的
窗口内部

已接收但尚未按序（乱序到达）的数据，被 TCP 缓存在接收缓冲区中，但不能被确认 - 累积确认，只能确认到连续的最高序号

尚未收到但预期会收到的数据 - 空闲

窗口右侧：不应接收；若收到通常丢弃

流量控制 Traffic Control

Follow control
接收方在每个 ACK 报文中，通过 Window 告知发送方自己的接收窗口 rwnd 大小 - 控制发送方不要发太快，以便接收方能来得及处理
发送方根据该值动态调整自己的发送窗口大小，确保不会发送超过接收方处理能力的数据
发送方可以多次发送；直到把发送窗口已满
接收方采用累计确认
0窗口 Zero Window
当接收方缓冲区满时，会通告窗口大小为 0

ACK = 1; rwnd = 0

发送方停止发送数据
但若之后接收方有空间了，却因 ACK 丢失等原因未能及时通知发送方，双方可能陷入死锁 - 双方无限等待
TCP 为每个连接都创建了一个持续计时器 persistence timer
只要发送方收到0窗口，就启动计时器。计时到，就主动发送一个窗口探测报文 Window Probe，以便恢复正常数据通信
接收方收到后必须回复 ACK，并携带当前真实窗口大小

ACK = 1; rwnd = 200

发送方收到后，恢复传输
若收到窗口仍为 0，则重启计时器，继续等待

ACK = 1; rwnd = 0

四次挥手 Four-Way Handshake
发送方没有数据要发送，发送释放连接FIN请求；接收方确认后，可以继续发送自己还未发送完的数据；当前连接是半连接状态：发送方到接收方的连接是关闭的
接收方发完数据了，也向发送方发送释放连接FIN请求；等链路上所有的数据报都达到目标主机后，连接被彻底释放
