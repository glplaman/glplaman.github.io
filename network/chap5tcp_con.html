闭环控制措施 Method
方案1. 在IP/分组头部设置拥塞指示位

在 IP 头部和 TCP 头部保留特定比特（如ECT、CE位）

当路由器检测到拥塞（如队列过长），不丢包，而是将转发的分组中的CE（Congestion Experienced）位设为1

接收方收到该分组后，在 ACK 中告知发送方网络曾拥塞

发送方据此降低发送速率

优点：避免丢包作为拥塞信号，提高效率；适用于支持 ECN 的端系统和网络设备

方案2. 通过丢包隐式传递拥塞信号

传统 TCP 机制 如 Reno、Cubic

路由器在缓冲区满时直接丢弃分组

发送方通过 超时重传或重复ACK 推断网络拥塞

于是执行拥塞避免算法，如慢启动、拥塞窗口减半

缺点：反应滞后，且丢包本身浪费带宽

TCP的拥塞控制

TCP 采用基于 滑动窗口 进行拥塞控制，属于闭环控制方法
TCP 发送方维持一个拥塞窗口 cwnd - Congestion Window
拥塞窗口的大小取决于网络的拥塞程度，且动态变化
发送端利用拥塞窗口根据网络的拥塞情况调整发送的数据量
发送窗口大小不仅取决于接收方窗口，还取决于网络的拥塞状况
swnd = min[rwnd, cwnd]
rwnd < cwnd
接收方的接收能力限制发送窗口的最大值
接收方的接收缓冲区已接近满，即使网络通畅（cwnd 很大），也不能继续发送更多数据，否则会导致接收方丢包
示例：餐厅厨房（发送方）可以快速做菜（网络通畅），但顾客（接收方）胃容量有限（缓冲区小），所以不能一直上菜
cwnd < rwnd
网络拥塞限制发送窗口的最大值
接收方还有充足缓冲区（rwnd 很大），但网络出现拥塞（如丢包、延迟增加），发送方主动减小 cwnd 以避免加剧拥塞
示例：顾客胃口很大（接收缓冲区充足），但外卖骑手堵在路上（网络拥塞），餐厅只能少量多次送餐，避免订单堆积

核心阶段 Phase
假设TCP的报文长度 MSS 固定为 1000byte
每个阶段的报文序号从0开始
阶段1. 慢开始 Slow Start
在连接初期或超时后，快速探测网络可用带宽
拥塞窗口 cwnd 从 1 MSS 开始
每收到一个对新报文段的确认 ACK，cwnd 增加 1 MSS → 每轮次 RTT 翻倍，指数增长
当 cwnd 达到慢开始门限 ssthresh（Slow Start Threshold）时，退出慢开始阶段 → 转入拥塞避免阶段

当 cwnd ≤ ssthresh 时，使用慢开始算法

当 cwnd > ssthresh 时，停止使用慢开始算法，改用拥塞避免算法

当 cwnd = ssthresh 时，既可使用慢开始算法，也可使用拥塞避免算法

TCP 通过每个被确认的段来驱动 cwnd 增长，而不是每个 ACK 报文

即使只收到一个累计 ACK，只要它确认了 k 个新段，cwnd 就增加 k 个 MSS

[] 解读
初始 cwnd = 1MSS - 只能发一个报文
发送方发送一个报文 M1
接收方收到 M1 后，发送1个 ACK 确认
发送方调整 cwnd + 1 =2MSS；允许发2个报文
发送方发送 M2 M3
接收方收到 M2 M3 后，发送2个 ACK 确认
发送方调整 cwnd + 2 = 4MSS；允许发4个报文
发送方发送 M4 M5 M6 M7
接收方收到 M4 M5 M6 M7 后，发送4个 ACK 确认
发送方调整 cwnd + 4 = 8MSS；允许发4个报文
结论：每个轮次RTT后，cwnd 翻倍
阶段2. 拥塞避免 Congestion Avoidance
触发条件：cwnd ≥ ssthresh
cwnd变化：每经过一个往返时间 RTT，期间不管收到多少 ACK，cwnd 都只增加 1 MSS - 线性增长

让拥塞窗口 cwnd 缓慢地增大，避免出现拥塞

可能的阶段转移
情况1：发生超时，判定为严重拥塞
触发条件：重传定时器超时，未收到预期 ACK
原因推测：网络严重拥塞、链路中断或大量分组丢失
调整：

慢开始门限 ssthresh = max (cwnd/2，2)

拥塞窗口 cwnd = 1

执行慢开始算法
重新进入阶段1 慢开始
情况2：收到3个重复 ACK，判定为轻度丢包
触发条件：连续收到3个或以上对同一数据序号的重复确认
原因推测：单个或少数分组丢失，但后续分组已到达接收方，网络仍有容量
应对措施：

立即触发阶段3 快重传，重传丢失分组

紧接着进入阶段4 快速恢复，而非回到慢开始

优势：避免因单点丢包导致吞吐量骤降，提升高带宽延迟积网络性能
阶段3. 快重传 Fast Retransmit
设计目标：尽早检测并重传丢失的报文段，避免因等待重传定时器超时而造成不必要的传输延迟
触发机制：重复确认，即连续收到三个重复的确认，就立即启动快重传，无需等待超时
整个网络的吞吐量提高约 20%
重传后，进入阶段4 快速恢复

M3丢失
接收方收到M1、M2、M4、M5、M6、M7
重复发起对M3的确认，希望接收M3

阶段4. 快恢复 Fast Recovery
设计目标：快重传后，避免退回到慢启动（过于保守），维持较高吞吐
触发机制：当发送端收到连续三个重复的确认
调整

慢开始门限 ssthresh = cwnd / 2

新拥塞窗口 cwnd = ssthresh

进入拥塞避免阶段，使拥塞窗口缓慢地线性增大（加法增大 AI）
前提：认为网络只是轻微拥塞（个别丢包），而非严重崩溃
拥塞控制四阶段
阶段 触发条件 cwnd 增长方式 目的
1. 慢开始
Slow Start		 初始或超时后 每 RTT 翻倍/指数增长 快速探测可用带宽
2. 拥塞避免

Fast Recovery		 快重传之后 cwnd = ssthresh
每收到一个重复 ACK 加 1，直到新 ACK 到达		 在不降速到 1 的情况下恢复传输
说明 Notation
为什么实现中用 MSS 作为单位？

避免频繁做乘除运算

发送时按“段”处理，天然以 MSS 为粒度

拥塞控制算法（如慢启动：每 RTT 翻倍 cwnd）在“段数”层面更直观

但对外表现和最终决策必须基于字节，因为

接收窗口是字节

应用层数据是字节流

流量控制和拥塞控制的交集必须单位统一
