概述 Overview

用户数据报 UDP - User Datagram Protocol
  1. 连接与状态

    无连接 (Connectionless)：无需建立连接，也不维护连接状态

    支持单播、组播、广播：灵活适应多种通信模式

  2. 可靠性

    最大努力交付 (Best-effort)：不保证交付，存在丢包可能

    无确认、不重传：发送后不等待确认，丢失也不重发

    不排序：不保证数据按发送顺序到达

  3. 传输控制

    无流量控制：发送方不会因接收方处理慢而减速

    无拥塞控制：网络拥堵时也不会降低发送速率

  4. 报文处理

    面向报文：不分段 (No segmenting)、不重组 (No reassembling)

    无序列号：不实现序列号机制

  5. 首部开销

    极小开销：首部仅 8 Bytes，远小于 TCP

路由信息协议 RIP(Routing Information Protocol)
应用层协议，依赖于用户数据报 UDP(User Datagram Protocol) 传输数据
需要指定一个 UDP 端口号 - 520，用于标识 RIP 报文
下行 ↓：RIP 报文封装在 UDP 数据报中，对应协议号 17，再由 IP 层传输
上行 ↑：IP 封装的数据报要交给上层的 UDP 处理；UDP 的数据要交给上层的 RIP 处理
为什么 OSPF 没有分配端口？
  1. 网络层协议
  2. UDP 提供的服务太简单
  3. 协议定位不同

    RIP 是简单的距离矢量协议，路由信息更新频繁，且对实时性要求较高(TCP 的三次握手和重传机制有延迟)

    OSPF 是复杂的链路状态协议，需要更精细的控制

  4. TCP 的重传机制太笨重

    TCP 如果丢包，会从头开始重传整个窗口的数据

    OSPF 有自己的确认与重传机制（如 LSAck 显式确认、邻居状态机、定期刷新 LSA）

    OSPF 只需要重传丢失的那一条 LSA（链路状态通告），而不是整个数据库

  5. TCP 连接开销大

    OSPF 需要和多个邻居建立邻接关系（比如一个路由器有 10 个邻居）。如果每个邻居都建一个 TCP 连接，开销巨大

    OSPF 直接使用 IP 组播（224.0.0.5 和 224.0.0.6），效率极高

  6. TCP 面向字节流

    OSPF 面向报文(Hello、DD、LSR、LSU、LSAck)

检测 UDP 用户数据报在传输中是否有错。有错就丢弃
伪首部：源IP地址、目标IP地址、IP协议号17、UDP长度和填充
校验内容：伪首部 + UDP首部 + UDP数据
校验覆盖“伪头部 + 头部 + 数据”，但这个校验值在组装报文时就已经算好了，放在头部字段里一起发送，不需要再额外加个尾部
发送方
  • 填上伪首部：不是真正发送的数据，仅用于 UDP 检验和的计算
  • 全0填充校验和字段
  • 伪首部+首部+数据三部分采用二进制反码求和
  • 求和结果填入校验和字段并发送UDP报文
  • 注意：最高进位必须加进去
接收方
  • 填上伪首部
  • 伪首部 + 首部 + 数据三部分采用二进制反码求和
  • 结果全为 1 则无差错；否则丢弃

二进制反码求和：在二进制加法的基础上多了一个规则：产生的进位 Carry，不丢弃，而是加到最低位（第0位）- 循环进位 End-around Carry

运算过程：按位相加 → 循环进位 → 最终取反

报文大小
若报文太长，IP 层在传送时可能要进行分片，形成多个 IP 分组 Packets
若报文太短，会使 IP 数据报的首部的相对长度太大，降低 IP 层的效率
受网络层 1500 Bytes 的 MTU 限制，建议应用层报文大小 ≤ 1472 Bytes，避免分片

    Checksum：the 16-bit one's complement of the one's complement sum of a pseudo header of information from the IP header, the UDP header, and the data, padded with zero octets at the end (if necessary) to make a multiple of two octets.
