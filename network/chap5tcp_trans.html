概述 Overview

TCP - Transmission Control Protocol
面向连接的协议
连接管理就是使 TCP 连接的建立和释放都能正常地进行
  1. 连接建立 - 三次握手
  2. 数据通信
  3. 连接释放 - 四次挥手

三次握手 Three-Way Handshake

TCP 连接的建立采用客户服务器 C/S 方式
主动发起连接建立的应用进程叫做客户 C - Client
被动等待连接建立的应用进程叫做服务器 S - Server
关注 Focus
要使每一方能够确知对方的存在
要允许双方协商一些参数（如最大窗口值、是否使用窗口扩大选项和时间戳选项以及服务质量等）
能够对运输实体资源（如缓存大小、连接表中的项目等）进行分配
实现方案 Solution
借助报文的控制位和序号实现
客户和服务器之间交换三个 TCP 报文段
客户端 C 主动发起连接；选择初始序号为 x
服务器 S 被动接受连接；选择初始序号为 y
第一次握手 SYN
C 向 S 主动发出连接请求报文段，进入 SYN_SENT 状态
消耗一个序号
不能携带数据
seq=x SYN=1
第二次握手 SYN+ACK
S 收到连接请求报文段后，如同意，则发回确认，进入 SYN_RCVD 状态
消耗一个序号
不能携带数据
seq=y ack=x + 1 SYN=1 ACK=1
第三次握手 ACK
C 收到此报文段后向 S 给出确认，进入 ESTABLISHED 状态
可以携带数据
如果不携带数据，则不消耗序号；但是下次发数据仍从 x+1 开始
seq=x+1 ack=y + 1 ACK=1
说明 Notation
TCP 的序号是为数据字节服务的
第三次握手的 ACK 报文本身不包含数据，所以它虽然设置了 seq=x+1，但不产生实际数据字节
因此，这个序号不会被真正使用或消耗
后续发送数据时，仍然可以从 x+1 开始
但如果携带了数据，则这些数据会占用序号空间，属于消耗
连接参数的协商，绝大多数都是通过 TCP 头部中的 Options 字段传递：MSS、Window
使用了 Options 后，TCP 首部的偏移就不再是 5（最小值），还要加上 Options 的字节数

四次挥手 Four-Way Handshake

TCP 连接释放过程比较复杂
因为支持全双工通信，双方必须都要确认通信完毕才可以释放连接
TCP 连接释放采用四报文握手
第一次挥手
C 没有数据要发送；发出连接释放报文段，主动关闭 TCP 连接
进入 FIN_WAIT_1 状态，等待 S 的确认
seq=u FIN=1
第二次挥手
S 发出确认
S 进入 CLOSE_WAIT 状态；通知高层应用进程；从 C 到 S 这个方向的连接就释放了，TCP 连接处于半关闭 Half-Close 状态
S 可以指定序号 seq=v，继续发送数据
C 收到确认后，进入 FIN_WAIT_2 状态
seq=v ack=u+1 ACK=1
第三次挥手
S 发完数据；通知 TCP 释放连接；再次确认 C 的释放连接
S 进入 LAST_ACK 状态；同时启动一个重传定时器（retransmission timer）
如果在超时时间内没收到 C 的 ACK（第 4 次挥手），B 会重传 FIN
seq=w ack=u+1 FIN=1 ACK=1
第四次挥手
C 收到连接释放报文段后，发出确认
C 进入 TIME_WAIT 状态；持续 2×MSL，C 才释放 TCP 连接
S 收到确认后，进入 CLOSED 状态，连接彻底释放
seq=u+1 ack=w+1 ACK=1
MSL（Maximum Segment Lifetime）
表示 TCP 报文段在网络中能够存在的最长时间，即最大生存时间
超过 MSL 后，该报文段应被所有路由器或主机丢弃，不再传递
典型值：30 秒、60 秒、120 秒（不同系统可配置，RFC 建议不超过 2 分钟）
主动关闭方在发送最后一个 ACK 后，会进入 TIME_WAIT 状态，并持续 2MSL 时间，然后才真正释放连接
确保对方收到最后的 ACK（可靠性）

有足够时间接收 B 可能重传的 FIN

防止旧连接的报文干扰新连接（避免“迟到的报文”问题）

确保网络中所有属于旧连接的报文都已过期

说明 Notation
S 释放连接时，再次确认 u+1，是因为 TCP 要求每个报文段都必须包含最新的确认号，即使该确认号与之前相同。这是协议设计的一部分，确保状态同步
C 最后报文使用 seq=u+1 是它下一个发送序号，符合 TCP 序号递增规则。即使没有数据，ACK 报文也必须携带正确的 seq，以维持协议状态一致性和防重放
四次挥手在实际网络中，考虑到重传的因素，可能变成 4 次、6 次、8 次……报文交互，但逻辑上仍是四步

应用层通知传输层关闭连接

应用程序发送一个 FIN 报文：结果是 TCP 进程发送一个 FIN

应用程序发送“关闭”报文：执行 API，如 close()，触发 TCP 进程发送一个 FIN

TCP 状态机 State Machine

共11个状态
  1. LISTEN – LISTEN is state I and it represents waiting for a connection request from any remote TCP host.
  2. SYN-SENT – SYN-SENT is state II and it represents waiting for a machine connection request after sending a connecting request.
  3. SYN-RECEIVED – SYN-RECEIVED is state III and it represents waiting for confirmation of connection acknowledgement after both sender and receiver has sent / received connection request.
  4. ESTABLISHED – It is state IV and represents an open connection, data received to be delivered to the user.
  5. FIN-WAIT 1 – FIN-WAIT 1 is state V and it represents waiting for a connection termination request from remote TCP host or acknowledgment of connection termination request sent previously.
  6. FIN-WAIT 2 – It is state VI and represents waiting for connection termination request from remote TCP host.
  7. CLOSE-WAIT – CLOSE-WAIT is state VII and it represents waiting for a connection termination request from local user.
  8. CLOSING – It is state VIII that represents waiting for a connection termination request acknowledgement from remote TCP host.
  9. LAST-ACK – LAST-ACK is state IX of TCP, which represents waiting for connection termination request acknowledgement previously sent to remote TCP host including its acknowledgement of connection termination request.
  10. TIME-WAIT – It is state X and represents waiting sufficient time to pass to ensure remote TCP host received acknowledgement of its request for connection termination.
  11. CLOSED – CLOSED is state XI. It is a fictional state and represents no connection state
[T5-33] TCP 连接处于 ESTABLISHED 状态。以下的事件相继发生：
1. 收到一个 FIN 报文段。
2. 应用程序发送一个 FIN 报文。
在每一个事件之后，连接的状态是什么？在每一个事件之后发生的动作是什么？
答：

事件1.

连接状态从 ESTABLISHED 变为 CLOSE-WAIT（关闭等待）

TCP协议栈立即向发送方回复一个 ACK 报文段，确认序号为收到的FIN序号加1

通知上层应用程序“对方已经发送完数据了”（即收到对方的关闭请求）

此时进入被动关闭流程。虽然收到了对方的FIN，但本端应用程序可能还有数据要发送，因此TCP连接处于半关闭状态，允许本端继续发送数据

事件2.

连接状态从 CLOSE-WAIT 变为 LAST-ACK（最后确认）

发送后，本端不再发送数据，开始等待对方对这个FIN的确认（ACK）

一旦收到对方的ACK，连接将彻底断开进入 CLOSED 状态

[T5-34] TCP连接处于SYN-RCVD状态。以下的事件相继发生：
1. 应用程序发送“关闭”报文。
2. 收到FIN报文段。
在以上的每一个事件之后，连接的状态是什么？在每一个事件之后发生的动作是什么？
答：

事件1.

应用程序发送“关闭”报文，触发 TCP 进程关闭链接

进入 FIN-WAIT-1 状态

处于 SYN-RCVD 状态的本端（服务器端）向对端发送 FIN 报文段，停止发送数据，并等待对端对 FIN 的确认

事件2.

进入 CLOSING 状态；本端事件1发了FIN，对端现在也发了FIN

收到对端的 FIN，本端必须发送 ACK 确认

[T5-35] TCP 连接处于 FIN-WAIT-1 状态。以下的事件相继发生：
1. 收到 ACK 报文段。
2. 收到 FIN 报文段。
3. 发生了超时。
在以上的每一个事件之后，连接的状态是什么？在每一个事件之后发生的动作是什么？
答：

事件1.

进入状态 FIN-WAIT-2

不用发送报文

事件2.

进入状态 TIME-WAIT

发送对 FIN 的 ACK

事件3.

进入状态 CLOSED
