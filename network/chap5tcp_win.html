滑动窗口

@Window
概述 Overview
TCP支持全双工通信
通信的双方各自维护一个发送窗口和接收窗口，共4个窗口
简单起见，我们只考虑一个方向的通信
发送窗口 swnd - Sender Window
发送方维持一个发送窗口，位于发送窗口内的分组都可被连续发送出去，而不需要等待对方逐个确认
发送窗口滑动：发送方每收到一个分组确认，就把发送窗口向前滑动一个分组的位置；已确认的数据被移出窗口
累积确认 Cumulative Acknowledgment：接收方对按序到达的最后一个分组发送确认，表示：到这个分组为止的所有分组都已正确收到了
发送窗口大小以 Byte 为单位
发送窗口大小由 接收方 决定：通过 TCP 报文中的 Window 字段告知发送方自己还能接收多少数据
发送方根据这个 Window，准备相应的数据发送并等待确认
窗口应用
假设发送窗口大小 = 4，当前可发送分组 [1, 2, 3, 4, 5, 6, ...]
分组 1 - 4 进入发送窗口并发送
在未收到任何确认之前，无法再发送数据
收到 Ack = 3，表示 1、2 已收到，等待接收 3
1、2 移出窗口，后面的分组补进来并发出去，等待发送、确认
其它没有收到确认的 3、4，保留，以备超时重传
窗口滑动到 [3, 4, 5, 6]
已知发送窗口大小为 500 Bytes。某主机收到的确认号为 201。如果已经发送了 300 Bytes，则还可以发送多少数据？
答：

发送了 300 Bytes，对方确认了 200 Bytes

还有 100 Bytes 没有确认

确认过的数据报被移出缓存，窗口仅仅保留没有确认的数据报

窗口还有 100 Bytes 等待确认

窗口大小是 500 Bytes，所以还可以发送 500 - 100 = 400 Bytes

接收窗口 rwnd - Receiver Window
接收方维持一个接收窗口，告诉发送方自己还能接收多少数据
接收方根据处理情况动态调整窗口大小，实现 流量控制 Flow Control
窗口左侧是已经已经按序到达且确认过的
窗口内部

已接收但尚未按序（乱序到达）的数据，被 TCP 缓存在接收缓冲区中，但不能被确认 - 累积确认，只能确认到连续的最高序号

尚未收到但预期会收到的数据 - 空闲

窗口右侧：不应接收；若收到通常丢弃
[T5-06]假定使用连续 ARQ 协议，发送窗口大小是 3，而序号范围是 [0, 15]，而传输信道保证在接收方能够按序收到分组。在某一时刻，在接收方，下一个期望收到的序号是 5。试问：
(1) 在发送方的发送窗口中可能出现的序号组合有哪些？
(2) 接收方已经发送出的、但在网络中（即还未到达发送方）的确认分组可能有哪些？说明这些确认分组是用来确认哪些序号的分组。
答：

接收≠确认

5是接收方希望接收的分组；说明：发送方发送了0、1、2、3、4分组；接收方已经收到了0、1、2、3、4分组；但是接收方对应的确认可能还没有达到发送方

发送方的发送窗口是3。保留的分组可能是

[2、3、4]：5都没有发送，因为2、3、4还没有被确认

[3、4、5]：5发送了，但是3、4、5都没有被确认

[4、5、6]：5、6发送了，但是4、5、6都没有被确认

[5、6、7]：5、6、7发送了，但是5、6、7都没有被确认

接收方发出的在途确认分组可能是：2、3、4；接收方还没有收到5，自然不能发送对5的确认
