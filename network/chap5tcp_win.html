滑动窗口

@Window
TCP支持全双工通信
通信的双方各自维护一个发送窗口和接收窗口，共4个窗口
简单起见，我们只考虑一个方向的通信
发送窗口 swnd - Sender Window
发送方维持一个发送窗口，位于发送窗口内的分组都可被连续发送出去，而不需要等待对方逐个确认
发送窗口滑动：发送方每收到一个分组确认，就把发送窗口向前滑动一个分组的位置；已确认的数据被移出窗口
累积确认 Cumulative Acknowledgment：接收方对按序到达的最后一个分组发送确认，表示：到这个分组为止的所有分组都已正确收到了
发送窗口大小以字节为单位
发送窗口大小由接收方决定：通过 TCP 报文中的 Window 字段告知发送方自己还能接收多少数据
[] 窗口应用
假设发送窗口大小 = 4，当前可发送分组 [1, 2, 3, 4, 5, 6, ...]
分组 1 - 4 进入发送窗口并发送
在未收到任何确认之前，无法再发送数据
收到 ACK=3，表示 1、2 已收到，等待接收 3
1、2移出窗口，后面的分组补进来并发出去，等待发送、确认
其它没有收到确认的 3、4，保留，以备超时重传
窗口滑动到 [3, 4, 5, 6]
[] 已知发送窗口大小为500byte，某主机收到的确认号为201。如果已经发送了300byte的数据，则还可以发送多少数据？
发送了300byte，对方确认了200byte
还有100byte没有确认
确认过的数据报被移出缓存，窗口仅仅保留没有确认的数据报
窗口还有100byte等待确认
窗口大小是500byte，所以还可以发送 500 - 100 = 400byte
接收窗口 rwnd - Receiver Window
接收方维持一个接收窗口，告诉发送方自己还能接收多少数据，用于 流量控制
根据接收窗口的大小动态通知发送方 - 流量控制 Flow Control
窗口左侧是已经已经按序到达且确认过的
窗口内部

已接收但尚未按序（乱序到达）的数据，被 TCP 缓存在接收缓冲区中，但不能被确认 - 累积确认，只能确认到连续的最高序号

尚未收到但预期会收到的数据 - 空闲

窗口右侧：不应接收；若收到通常丢弃
