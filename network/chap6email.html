邮件发送和邮件读取协议
邮件发送和读取使用不同的协议
简单邮件发送协议 SMTP：在用户代理向邮件服务器或邮件服务器之间发送邮件
邮局协议 POP3：用户代理从邮件服务器读取邮件
SMTP（发）和 POP3（收），是两个独立的、方向相反的动作
推 Push vs 拉 Pull
为什么采用不同的协议设计
1. 职责不同/应用场景不同
发送时通常不需要验证收件人是谁（只需要验证发件人身份）
而接收时必须验证用户身份（账号密码），否则谁都能看你的邮件
2. 行为模式不同
从客户端把邮件推给服务器，或者从一个服务器把邮件推到另一个服务器。接收方一直在那里等着收
让用户主动连接到服务器，把存好的邮件拉下来。如果是用 SMTP 接收，服务器就需要主动推给你，但这在动态 IP、防火墙和离线存储的场景下非常困难
SMTP/POP3 VS HTTP
核心模型：邮件是存储-转发；HTTP是请求-响应
角色定位：邮件协议是双向主动：SMTP 中，主动发/推；POP3 中，用户主动收/拉；HTTP 中，永远是客户端主动发起连接，服务器被动响应
设计目标：专用和通用

SMTP 诞生于 1982 年（甚至更早），而 HTTP 诞生于 1990 年

在 HTTP 出现之前，邮件系统已经建立了一套完整的生态，且工作得很好

如果让全球所有的邮件服务器改用 HTTP，成本极高，且没有这个必要

SMTP 服务器发出服务就绪 - 协议规定；并不是所有协议都由客户端先发
SMTP 客户向服务器发送问候 HELO 命令，附上发送方的主机名
SMTP 服务器若有能力接收邮件，则回答：“250 OK”，表示已准备好接收
对比 TCP 的 0 窗口的处理机制

2.1. 信封阶段（Envelope Phase）
目的：告诉服务器“谁发的”、“给谁发”
使用命令：

MAIL FROM: - 指定发件人

RCPT TO: - 指定收件人

服务器返回 250 OK 表示接受

2.2. 内容阶段（Data Phase）
目的：传输邮件内容（包括首部和正文）
使用命令：

DATA - 告诉服务器接下来是邮件内容

服务器回复 354 Start mail input... 表示可以开始输入

内容以 <CRLF>.<CRLF> 结束（即空行后跟一个点）

- 只有当一个行只包含一个单独的点（.）时，才被视为结束标志

- 点前面必须有 <CRLF>；点后面也必须有 <CRLF>

- 是传输控制指令。它不属于邮件本身

封装过程
  1. 封装 Header
  2. 添加空行
  3. 封装 Body
  4. 添加结束标记 <CRLF>.<CRLF>

填表（Header） -> 画线（空行） -> 写信（Body） -> 贴封条（<CRLF>.<CRLF>）

邮局协议 POP3

Post Office Protocol version 3
邮件接收协议之一
3 表示第3个版本
基于 TCP 使用客户/服务器 - C/S 方式
端口 110：标准 POP3 端口（明文或 STARTTLS）
端口 995：POP3S（POP3 over SSL/TLS），加密连接
用户连接服务器 → 一次性下载所有新邮件 → 默认从服务器删除
基本流程
  1. 客户端连接 POP3 服务器（端口 110）
  2. 认证（用户名/密码）
  3. 列出邮件列表（LIST 命令）
  4. 下载邮件（RETR 命令）
  5. 标记为删除（DELE），退出时真正删除（QUIT）
特点
无法多设备同步：在手机上读了邮件，电脑上看不到“已读”状态
容易丢失邮件：如果本地设备损坏且服务器已删邮件，数据无法恢复
功能单一：不能远程管理文件夹、搜索服务器内容等
去邮局取信；取完信，邮局就没有你的信件了

互联网信息访问协议 IMAP

邮件接收协议之一
Internet Message Access Protocol
IMAP（明文或 STARTTLS）：端口 143
IMAPS（SSL/TLS 加密）：端口 993
邮件始终保存在服务器上
客户端通过 IMAP 同步访问服务器上的邮件，所有操作都在服务器上完成，支持多设备实时同步
所有操作（读、删、移、标星）实时同步到所有设备
基本流程
  1. 客户端连接 IMAP 服务器（端口 143 或 993）
  2. 身份验证（用户名/密码）
  3. 获取邮箱列表（如收件箱、发件箱、草稿等）
  4. 同步邮件状态（未读/已读、星标、移动等）
  5. 实时操作（读、删、移、搜索、过滤）都会反映在服务器上
  6. 支持文件夹层级管理和邮件分类
特点
要想查阅邮件，必须先联网
占用服务器存储空间
对服务器性能要求高

POP3：适合只想下载邮件并离线阅读的用户，但缺乏同步能力

IMAP：适合需要多设备同步、远程管理、实时更新的现代用户，是当前主流选择

多用途互联网邮件扩展 MIME

Multipurpose Internet Mail Extensions
用于扩展电子邮件；支持

非 ASCII 字符（如中文、阿拉伯文等）

附件（如图片、音频、视频、PDF 等二进制文件）

多部分消息体（例如：一封邮件同时包含纯文本和 HTML 版本）

是邮件内容的编码方式
不是传输协议，因此不绑定端口号
定义了：

如何标识内容类型（Content-Type）

如何对非 ASCII 数据进行编码（如 Base64）

如何将多个内容组合在一个消息中（multipart）

主要功能
1. 定义了 5 个新的邮件首部字段 Header Fields
这些字段嵌入在邮件头部，用于描述邮件内容的结构和编码方式
首部字段 Header Fields
item desc

包括：主类型 type 和子类型 subtype，中间用 / 分开

MIME 标准原先定义了 7 个基本内容类型和 15 种子类型

MIME 允许发件人和收件人自己定义专用的内容类型

为避免可能出现名字冲突，标准要求为专用内容类型选择的名字要以字符串 X- 开始

2. 定义了许多邮件内容的格式，对多媒体电子邮件的表示方法进行了标准化
支持非 ASCII 文本（如中文、日文、阿拉伯语等）
支持多种媒体类型：文本、图像、音频、视频、应用程序文件等
引入多部分（multipart） 结构，使一封邮件可包含多个独立部分（例如：正文 + 附件，或纯文本 + HTML 版本）
多部分 multipart 结构常见类型
item desc
multipart/mixed 混合内容（正文+附件）
multipart/alternative 同一内容的不同格式（如 text 和 HTML）
multipart/related 主文档与关联资源（如 HTML + 内嵌图片）
3. 定义了多种传送编码 Transfer Encodings
传统 SMTP 只支持 7-bit ASCII，无法直接传输二进制数据
接收方根据 Content-Transfer-Encoding 字段自动解码，还原原始内容
传送编码 Transfer Encodings
item desc
7bit 仅限 7-bit US-ASCII 字符
每行不能超过 1000 个字符（包括回车和换行）
适合纯英文文本邮件
默认编码方法
8bit 8 位非 ASCII 编码，每行不能超过 1000/998 个字节（包括回车和换行）
必须遵守行长限制
Binary 8 位非 ASCII 编码，任意长度的字节串
没有行长限制
图片、可执行文件、压缩包等二进制文件
Base64 将任意二进制（3字节）拆解重组为 4 个 7-bit ASCII 字符
适合图片、PDF、压缩包等二进制附件
Quoted-printable 英文/数字/常规标点原样发送
非 ASCII 字符（中文）或特殊字符转为 =XX (十六进制)
内容以纯文本为主，但包含少量中文或特殊符号的正文

Base64 编码
适合任意长度的二进制数据/字节序列
编码结果是 ASCII
规则
  1. 把二进制代码划分成一个个的 3byte/24bit 的单元
  2. 不足3byte的，要填充/补充至 3 的倍数，以便按 6bit 划分
  3. 每个单元划分成 4 个 6bit 组
  4. 每个 6bit 可以表示 64 值
  5. 根据编码得到编码结果
  6. 如果有补充字节

    补充 1 byte，则最后一个字符替换为 =

    补充 2 byte，则最后两个字符替换为 ==

  7. 用两个连在一起的二个等号 “==” 和一个等号 “=” 分别表示最后一组的代码只有 8 位或 16 位
  8. 回车和换行忽略
